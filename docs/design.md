# iPhone を Bluetooth マウス／キーボードにするアプリ：設計書

- 作成日：2026-11-17
- アプリ名（仮）：HIDPad
- 対象：個人利用（App Store には出さない）
- 状態：構成は確定し、実装済み（進み具合は §12）
- この文書が根拠として挙げるログ（`…/build/…log` など）と、作業中に退避したソース（`backups/`）は、端末名や識別子を含むためリポジトリには入れていない。

## 1. 目的と範囲

iPhone の画面をトラックパッドとキーボードにして、Mac やそのほかの Bluetooth 対応機器（Windows など）を操作する。

- 入力機能：ポインタ移動、クリック、ドラッグ、スクロール、キー入力、メディアキー
- 接続先：この Mac を第一の対象とし、Windows PC を第二の対象とする
- 対象外：画面の表示やファイル転送、iPhone がロック中・バックグラウンド中の操作

## 2. 結論

**iPhone 単体を標準の Bluetooth LE HID デバイス（HID over GATT）にする。** 接続先には受信用の常駐ソフトを入れない。

- iOS は HID サービスの UUID を16ビット短縮形（`1812`）で登録すると拒否する。128ビット正規形（`00001812-0000-1000-8000-00805F9B34FB`）なら受理する。
- macOS 27.2 は、128ビット形で登録した HID サービスを HID マウスとして扱った（§3）。
- この Mac は、アプリを起動すると 1.4〜1.9 秒で自動的に iPhone を HID デバイスとして認識する。Mac 側の操作もソフトも要らない（M0 の実測、§7.1）。
- Mac 用コマンド `mac-connect` は、接続が切れたあとの復旧と、テストでの観測に使う補助の道具とする。

当初想定していた「Mac 側の受信アプリでイベントを注入する構成」と「ESP32 などのハードウェア中継」は採らない。

測定環境：iPhone 17（iOS 27.3）、MacBook Air（macOS 27.2、Xcode 27.2）。測定コードは `spike/hid-probe`（iPhone 側）と `spike/mac-scan`（Mac 側）にある。

### 3.2 推定（未確認）

- Mac の Bluetooth 設定の一覧に出ないのは、利用者自身の iCloud に属する iPhone だからである（`bluetoothd` は一致を記録しているのに、設定画面が表示しない）。
- 既存の結び付きを持たない接続先（Windows、別の Apple ID の Mac）では、通常のペアリングが必要になる。
- サービスを登録し直すたびに接続先へ「サービス変更」が通知され、macOS 側の初期化が崩れる。測定アプリが登録・削除を繰り返していた回では HID デバイスが作られなかった。

### 3.3 未検証

U1・U2・U4・U5 は確認できた（§3.1）。残りは次のとおり。

| 番号 | 項目 | 設計への影響 |
|---|---|---|
| U3 の残り | Mac の Bluetooth の入れ直しや、Mac のスリープ復帰のあとに自動でつながり直すこと | つながり直さない場合に `mac-connect connect` で復旧できるかを確かめる。利用者の了承が要る操作なので未実施 |
| U7 | Windows が、アプリの再起動・iPhone の再起動・Windows の再起動のあとに自動でつながり直すこと | つながり直さない場合の手順を §7.2 に書く |

案 B（HID サービスを複数持つ構成）は、案 A が Mac と Windows の両方で通ったので測らない。

## 4. 全体構成

```
┌───────────── iPhone（HIDPad）─────────────┐          ┌──── 接続先 ────┐
│ 画面  TrackpadView / KeyboardView / HostsView │          │ OS 標準の        │
│        │ タッチ・キー                         │          │ HID ドライバ     │
│ HIDCore（純粋ロジック、Mac 上で単体テスト）   │  BLE     │                  │
│   PointerEngine / KeyMap / Reports            │  HOGP    │ Mac / Windows    │
│        │ レポートのバイト列                   │ ───────▶ │ ほか             │
│ BLEPeripheral（CoreBluetooth の薄い層）       │          │                  │
└───────────────────────────────────────────────┘          └──────────────────┘
                                                    Mac のみ：mac-connect が
                                                    最初の接続のきっかけを作る
```

設計上の決めごとは次の3点である。

1. **ロジックと通信を分ける。** レポートの組み立て、タッチからの変換、キー配列は `HIDCore`（Swift パッケージ）に置き、CoreBluetooth に依存させない。Mac 上の `swift test` で実機なしに検証できる。
2. **アプリ本体は薄くする。** 画面と CoreBluetooth の橋渡しだけを持つ。
3. **GATT は起動時に一度だけ組む。** サービスをすべて登録し終えてからアドバタイズを始め、以後は登録を変えない（§3.2 の推定への対処）。

## 5. GATT 設計

UUID は**すべて128ビット正規形**（`0000XXXX-0000-1000-8000-00805F9B34FB`）で書く。

| サービス | 特性 | プロパティ | 権限 | 値 |
|---|---|---|---|---|
| HID `1812` | HID Information `2A4A` | read | 暗号化必須 | `11 01 00 02`（bcdHID 1.11、国コード 0、通常接続可） |
| | Report Map `2A4B` | read | 暗号化必須 | §6 の記述子 |
| | HID Control Point `2A4C` | writeWithoutResponse | 暗号化必須 | サスペンド通知を受ける |
| | Protocol Mode `2A4E` | read, writeWithoutResponse | 暗号化必須 | `01`（Report Protocol） |
| | Report `2A4D`（入力、レポートごとに1個） | read, notify | 暗号化必須 | 記述子 `2908` =（レポート ID、種別 1） |
| | Report `2A4D`（出力、キーボード LED） | read, write, writeWithoutResponse | 暗号化必須 | 記述子 `2908` =（レポート ID、種別 2） |
| Device Information `180A` | Manufacturer Name `2A29` | read | なし | 任意の文字列 |
| | PnP ID `2A50` | read | なし | ベンダー ID の出所 2、ベンダー `0xFFFF`、製品・版は任意 |
| Battery `180F` | Battery Level `2A19` | read, notify | なし | iPhone の電池残量 |

- 特性の値は静的に持たせず、読み取り要求にその都度応える。
- アプリから `.extendedProperties` は付けない（iOS が自動で付ける分はそのままにする）。
- 購読を受けたら、基準となるゼロのレポートを1件送る。送らないと入力を受け付けない接続先がある。

### 5.1 レポートの分け方（U2 の結果で決める）

- **案 A（第一候補）**：HID サービス1個。Report Map にレポート ID 1〜3 を定義し、`2A4D` をレポートごとに持つ。
- **案 B（代替）**：HID サービスを機器ごとに1個ずつ持つ（マウス用、キーボード用）。レポート ID は使わない。レポート ID なしの Report Map は入力レポートを1種類しか持てないので、メディアキーを使うなら3個目の HID サービスが要る（`GATTLayout` の `includeConsumerService` で切り替える）。

**案 A で実装する。** Mac と Windows の両方で案 A が通った（§3.1）。案 B は `HIDCore` に定義だけ残す。どちらでも `HIDCore` が作るレポートの中身は同じで、変わるのは `BLEPeripheral` の GATT の組み方だけにする。

## 6. レポート定義

| ID | 種類 | 中身 | 長さ |
|---|---|---|---|
| 1 | マウス（入力） | ボタン5個＋詰め物3ビット、X（符号付き16ビット、相対）、Y（同）、縦ホイール（符号付き8ビット）、横スクロール AC Pan（符号付き8ビット） | 7バイト |
| 2 | キーボード（入力） | 修飾キー8ビット、予約1バイト、キーコード6個（使用 ID 0x00〜0xE7） | 8バイト |
| 2 | キーボード（出力） | LED 5ビット（Num、Caps、Scroll、Compose、Kana）＋詰め物3ビット | 1バイト |
| 3 | メディアキー（入力） | Consumer ページの使用 ID 1個（16ビット） | 2バイト |

- HID over GATT では、レポート ID は特性の値に含めない。`2908` 記述子で示す。
- キーボードの入力レポートは、ブートプロトコルと同じ並びにしておく。
- 日本語配列のキー（`¥` `ろ` `英数` `かな`）は、International 1・3 と LANG 1・2 の使用 ID を使う。

## 7. 接続

### 7.1 Mac（この Mac）

- **通常は何もしなくてよい。** iPhone でアプリを起動すると、Mac が 1.4〜1.9 秒で HID デバイスを作る。アプリを終了すると消える。
- これは、同じ利用者の Apple 製品同士が BLE 接続と結び付きを保っているために成り立つ。別の Apple ID の Mac では成り立たない見込みで、その場合の接続方法は未検証である。
- 「システム設定 > Bluetooth」の一覧には iPhone は出ない。接続の状態は、アプリの画面か `mac-connect status` で確かめる。
- `Tools/mac-connect` の役割は次の3つである。常駐せず、入力の中継もしない。
  - `connect`：接続が切れて自動で戻らないときに、Mac 側から接続のきっかけを作る（Bluetooth の入れ直しやスリープ復帰のあとに要るかは U3 の残り）
  - `status`：Mac が認識している BLE の HID デバイスと、その構成を表示する
  - `monitor`：BLE の HID デバイスから届いた入力値を記録する（テストでの観測用）
- **不具合時に Mac で「このデバイスを削除」を案内しない。** この Mac と iPhone の結び付きは、Apple 製品同士の連携に使われているものと同じ可能性がある。

### 7.2 Windows などの接続先

- 接続先の Bluetooth 設定から、通常の手順でペアリングする。iPhone 側にペアリングの確認が出る。Windows 11 で通ることを確認した（§3.1）。
- **以前その接続先と iPhone をペアリングしたことがある場合は、先に両側の古い情報を消す。** 接続先で iPhone を削除し、iPhone の「設定 > Bluetooth」でも接続先の登録を解除する。片側に残っていると、接続先は iPhone を電話として従来型の Bluetooth でつなぎ、HID サービスを読まない（Windows では「その他のデバイス」に分類され、機能が PAN だけになる）。アプリの接続先画面に、この手順を説明として載せる。
- 接続先の一覧に、アドバタイズ上の名前（`HIDPad`）と iPhone の端末名の両方が出た場合は、アドバタイズ上の名前のほうを選ぶ。
- 接続後に表示される名前は、iPhone の端末名になる。アドバタイズ上の名前（`HIDPad`）とは別で、アプリからは変えられない。
- 機器の種別（Appearance）もアプリからは設定できない。接続先でのアイコンは汎用のものになる。
- ペアリング後に自動でつながり直すかは未確認である（U7）。

### 7.3 複数の接続先

- iPhone は複数の接続先と同時につながれる。入力レポートは、選択中の1台だけに送る（`updateValue(_:for:onSubscribedCentrals:)`）。
- 接続先は `CBCentral.identifier` で見分け、利用者が付けた名前（「MacBook」「デスクトップ」など）と対応させて保存する。
- 切り替えは `HostsView` で行う。

### 7.4 アドバタイズ

- 前面にいる間、HID サービスの UUID（アドバタイズ上は16ビット形）と名前 `HIDPad` を載せてアドバタイズする。
- バックグラウンドでは名前とサービス UUID が載らなくなるため、新規の発見はできない前提にする。
- バックグラウンド動作（`UIBackgroundModes: bluetooth-peripheral`）は有効にする。設定画面を開くなどで一時的に前面を離れても、接続先の HID デバイスが消えないようにするためである。操作できるのは前面にいる間だけ、という前提は変えない。

## 8. iPhone アプリの設計

### 8.1 `HIDCore`（Swift パッケージ）

| 型 | 役割 |
|---|---|
| `ReportDescriptor` | Report Map のバイト列を組み立てる。案 A 用と案 B 用の両方を出せる |
| `MouseReport` `KeyboardReport` `ConsumerReport` | レポートの値型と、バイト列への変換 |
| `PointerEngine` | タッチの列をポインタ移動・クリック・ドラッグ・スクロールに変える状態機械 |
| `KeyMap` | 文字や画面上のキーを、使用 ID と修飾キーの組に変える。US 配列と JIS 配列を持つ |
| `TextTyper` | 文字列を、押す・離すのレポート列に展開する |
| `ReportQueue` | 送信待ちの管理。相対移動は合算し、キーとボタンの変化は順序を保つ |
| `GATTLayout` | サービス・特性・記述子の構成を値として表す（CoreBluetooth に依存しない） |

`PointerEngine` の規則は次のとおり。

- **移動**：指1本の移動量に感度と加速度（速いほど大きく）を掛ける。端数は次回に持ち越す。
- **タップ**：短時間かつ移動が小さい接触を左クリックにする。指2本のタップは右クリックにする。
- **ドラッグ**：ダブルタップの2回目を押したまま動かすとドラッグにする。
- **スクロール**：指2本の移動を縦ホイールと横スクロールに変える。向きは設定で反転できる。
- 時刻は引数で受け取り、内部で時計を読まない（テストで再現できるようにする）。

利用者の指摘（2026-11-17）：指2本のスクロールは、片手で持った iPhone ではやりにくい。次の3つを加える。指2本のスクロールは残す。

- **スクロール帯**：タッチ面の右端に細い帯を設け、そこを指1本で上下になぞるとスクロールする。帯の位置（右／左）と幅は設定で変えられる。帯から始めた接触は、途中で帯の外に出てもスクロールのまま扱う。
- **慣性**：指を払って離すと、速さに応じてしばらくスクロールが続き、減速して止まる。触れ直すと止まる。慣性の計算は `PointerEngine` に時刻を渡して進める（内部で時計を読まない）。
- **速さに応じた加速**：ゆっくりなぞると細かく、速くなぞると大きく進む。
- 指2本の認識も見直す。2本目が少し遅れて触れた場合に、1本目の動きがポインタ移動として漏れないようにする。

### 8.2 `BLEPeripheral`（アプリ内）

- `@MainActor` のクラスで、`CBPeripheralManager(delegate:queue: .main)` を持つ。
- 起動時に `GATTLayout` から全サービスを一度だけ登録し、すべての登録完了を待ってからアドバタイズする。
- 送信は `ReportQueue` から取り出す。`updateValue` が `false` を返したら送信を止め、`peripheralManagerIsReady(toUpdateSubscribers:)` で再開する。待っている間の移動量は合算される。
- 購読を受けたら `setDesiredConnectionLatency(.low, for:)` を呼び、接続間隔を短くするよう求める。
- CoreBluetooth が投げる Objective-C 例外は Swift では捕まえられない。登録・アドバタイズ・応答の呼び出しは、Objective-C の `@try/@catch` の小さな補助関数で包む。
- `CBUUID` は `Sendable` ではない。定数は計算型の `static var` で持つ。

  - 設定と接続先の詳細は、上の隅の小さなアイコンの奥に置く
  - キーパネルと文字入力は、下のボタンの領域と入れ替わる形で出す。タッチ面は小さくなるが使える

  - 接続先の Bluetooth 上の名前を自動で取れるか試す（`CBCentralManager.retrievePeripherals(withIdentifiers:)` で同じ識別子の `name` を読む）。取れるかどうかは実機で確かめる

### 8.4 文字入力の方針

1. **キーパネル**：使用 ID をそのまま送る。配列の影響を受けないキー（矢印、修飾、ファンクション）はこれで足りる。
2. **文字入力欄**：iOS のソフトウェアキーボードで打った文字を `KeyMap` でキー操作に直して送る。対象は ASCII の範囲に限る。記号の位置は接続先の配列設定（US／JIS）に依存するため、設定で選ばせる。
3. **日本語**：変換済みの文字は送れない。`かな` キーで接続先の日本語入力を有効にし、ローマ字を送って接続先側で変換する。
4. **iPhone につないだ外付けキーボード**：`UIPress` の `keyboardHIDUsage` をそのまま中継する（後の段階で対応）。

利用者の要望（2026-11-17）で、3 の方針を次のように改める。**iPhone の日本語フリック入力をそのまま使えるようにする。**

- HID のキーボードはキーコードしか送れず、文字そのもの（Unicode）は送れない。そこで、フリック入力で届いたかなを、ローマ字のキー操作に直して送る。接続先の日本語入力（ローマ字入力）がそれをかなに戻す。
- 変換と確定は接続先の日本語入力で行う。フリックキーボードの「空白」が Space（変換）、「確定／改行」が Return（確定）として届く。
- かなは1文字ずつ独立に直す。小書きのかなは `xya` `xtu` のような単独で打てる綴りにし、「ん」は `nn` にする。フリックキーボードは濁点や小書きへの切り替えで直前の文字を消して打ち直すので、1かなが接続先の1かなに対応していなければならない。
- ~~文字入力欄は `UIKeyInput` だけを実装する。~~ **この前提は誤りだった（2026-11-18、利用者の実機操作で判明）。** `UIKeyInput` だけの入力欄では、日本語フリックキーボードは打ったかなを一文字もアプリに渡さない。変換中の文字列（マークドテキスト）を受け取れる入力欄が要る。占有下の自動テストが通っていたのは、キーボードより下の層にかなを直接流していたためで、届き方そのものは検査していなかった。
- 改めた方式：入力欄を本物の `UITextView` にし、変換中の文字列の変化を読んで接続先に写す。
  - 変換中の文字列がかなのまま伸び縮みする間は、差分を写す（増えたかなはローマ字、減ったかなは Backspace）。
  - iPhone 側で変換が始まって、変換中の文字列がかな以外になったら、接続先に Space（変換）を送る。
  - 確定された文字列が直前の変換中の文字列と同じなら、Return（確定）を送る。
  - 候補を直接選んだ場合（確定された文字列が直前の変換中の文字列と違う場合）は何も送らず、接続先の画面で変換・確定するよう表示する。接続先で、利用者が見ていない文字列を確定させないためである。
  - この対応づけは見込みであり、まず記録だけを取る版で、フリックキーボードが実際にどういう順で文字列を変えるかを確かめてから実装する。
- 入力モードの同期：接続先の状態を「不明／かな／英数」で持つ。不明のときは、最初のキーの前に必ず合わせる（iPhone が日本語キーボードなら `かな`、それ以外なら `英数`）。iPhone のキーボードの言語が変わったら、次のキーの前に合わせ直す。送り先の切り替え、前面への復帰、入力欄への移動、キーパネルの `かな`／`英数` の手動操作、長い無操作のあとは「不明」に戻す。同じキーを続けて2回は送らない。この自動切り替えは設定で止められる。
  - 当初の実装は「アプリ自身が `かな` を送ったあとにだけ `英数` を送る」という規則で、接続先が最初から日本語入力だった場合に英字がかなになってしまった。
  - Mac は入力モードを LED（かなランプ）では知らせてこない。状態は推測で持つしかない。
- 前提：接続先の日本語入力がローマ字入力であること。かな入力の設定には対応しない。
- 変換表は `spike/kana-romaji` で作り、macOS と Windows の標準のローマ字表の両方で通る綴りを選ぶ。できあがったら `HIDCore` に取り込む。

利用者の要望（2026-11-18）：**iPhone のキーボードで空白キーを長押しすると使えるカーソル移動を、接続先の矢印キーとして送る。** 下へなぞれば「↓」を押したことにする。

- iOS のこの機能は、入力欄の中のカーソル位置を動かすだけで、アプリに「なぞった」という通知は来ない。入力欄が空だと、カーソルが動く先がないので何も起きない。
- そこで、入力欄のカーソルの周りに見えない詰め物の文字（縦横の格子）を置き、カーソルが動けるようにする。カーソルの位置の変化を読み、横の移動量を「←」「→」、縦の移動量を「↑」「↓」の回数に直して送る。動きが止まったらカーソルを中央に戻す。
- 詰め物の文字は、接続先に送らず、変換中の文字列の処理にも混ぜない。入力欄そのものは見せなくなるので、変換中の文字列と案内は別の表示に出す。
- iPhone 側に変換中の文字列がある間は、矢印キーにしない（iOS がその文字列の中でカーソルを動かすため）。
- 矢印キーはキーの最短押下時間（§12）に従うので、毎秒 20 回程度が上限になる。速くなぞって回数が溜まった分は捨て、指を止めたあとに接続先のカーソルが動き続けないようにする。
- 接続先で変換結果が未確定のとき（候補をタップしたあと）は、この矢印キーで接続先の候補や文節を選べる。
- 設定でオフにできる。
- 実機で分かったこと（2026-11-18、`App/build/run-cursorpad-edge-feedback.log`）：
  - 長押しのカーソル移動は入力欄に届き、カーソルは1行・1文字ずつ動く。利用者が Mac で動作を確認した。
  - 格子は縦 15 行・横 33 列（この iPhone の入力欄の幅での値）。カーソルは格子の端で止まり、指を動かし続けても先へ進まない。指は四方の端まで届く。
  - 操作の途中でカーソルを中央に戻すと、数ミリ秒後に iOS が指の位置へ引き戻す。途中で戻す方法は使えない。
- そのため、**端での自動連打**にした。カーソルが格子の端に着いたまま指を置いていると、0.3 秒後からその方向の矢印キーを 0.1 秒ごとに送り、1.5 秒続くと 0.06 秒ごとに速める。指を戻すか離すと止まる。角では両方向に送る。連打の判定は `EdgeRepeater`（`HIDCore`）にある。途中で中央に戻す処理は外した。

JIS 配列には、M1 の実装で分かった注意点が2つある。

- **`\` の打ち方は接続先の OS で変わる。** macOS では Option＋`¥`、Windows では `¥` キー単体になる。配列（US／JIS）に加えて、接続先の OS（macOS／Windows）も設定で選ばせる。`KeyMap(layout:host:)` がこの2つを受け取る。
- **macOS がこの機器を JIS キーボードとして扱うとは限らない。** ANSI 扱いになると `¥` と `ろ` のキーは何も入力しない。扱いはベンダー ID・製品 ID や「キーボード設定アシスタント」で決まる可能性がある。M3 で実機確認し、必要なら HID Information の国コードを日本（15）にする、利用者に「キーボードの種類を変更」を案内する、のどちらかで対処する。

### 8.5 クリッカーモード（2026-11-18、利用者の要望）

発表のときに、iPhone をスライド送りとポインターのリモコンとして使うためのモード。

- **切り替え**：設定から有効にする。有効な間はキーボードのパネルと文字入力を出さない。接続先の選択と設定の入口は残す（終了は設定から）。
- **画面**：上半分をタップすると次のスライド、下半分をタップすると前のスライド。中央に丸いボタンを置く。画面を見ずに使うので、領域は大きく取り、次と前で振動を変える。
- **スライド送りのキー**：次は「→」、前は「←」を既定にする。PowerPoint（Windows・Mac）は、次に N・PageDown・→・↓・Space、前に P・PageUp・←・↑ を受け付ける（Microsoft の資料で確認）。PageDown／PageUp に変える設定を持つ。
- **ポインター**：中央のボタンを押している間、iPhone の向きの変化（ジャイロ）をポインタの移動に変える。離すと止まる。
  - 向きの変化は、重力の向きを基準に「左右に振る」「上下に振る」の成分に分ける。iPhone を傾けて持っても、左右に振れば横に動くようにするためである。
  - 計算は `HIDCore` に置き、角速度と時刻を引数で受け取る（内部でセンサーや時計を読まない）。感度は設定で変えられる。
- **PowerPoint のレーザーポインター**：接続先ごとに方式を選ぶ。
  - 「PowerPoint（切り替え）」：押したときにレーザーポインターを出すショートカットを送り、離したときに矢印へ戻すショートカットを送る。Windows は Ctrl+L と Ctrl+A、Mac は ⌘L と ⌘A（Microsoft の資料で確認）。接続先の OS の設定から選ぶ。
  - 「Ctrl＋左ボタン押しっぱなし」：Windows の PowerPoint では、Ctrl を押しながら左ボタンを押している間だけレーザーポインターが出る（Microsoft の資料には載っておらず、解説記事による）。
  - 「ポインタを動かすだけ」：キーは送らない。Keynote や PDF など、マウスのポインタそのものを指示に使う場合。
  - 既定は「PowerPoint（切り替え）」。
- **安全**：矢印キー、修飾キーとの組み合わせ、マウスのボタンは、自動テストで送ってはならない（§11.3）。判定は単体テストと、送信しない検査で確かめ、実際の動作は利用者が確かめる。

実装で決めたこと（2026-11-18、`swift test` は 276 件すべて通る）：

- スライド送りは、指を離したときに1回だけ送る。同じ半分で触れ始めて、そこから出ずに離した場合に限る。ポインターのボタンから始まった接触、反対の半分から滑ってきた接触、取り消された接触では送らない。見ずに握ったときの誤接触を捨てるためである。押し続けても連打しない。
- ポインターの出し方と感度は、接続先ごとに持つ。
- ポインターを離すときに送るキーは、押した時点で決める。押している最中に方式や接続先を変えても、対応がずれない。アプリが前面を離れたとき、接続先が変わったとき、モードを切ったとき、接触が取り消されたときも、必ず離す側を送る。
- 「Ctrl＋左ボタン押しっぱなし」の間は、スライド送りのタップを無視する。
- 接続先のメニューに「クリッカーモードを終了」を置いた。
- iPhone の動きの読み取り（Device Motion）は、iOS 27.3 では許可の確認なしで使えた（毎秒約 100 回）。静止時は移動量ゼロだった。`NSMotionUsageDescription` は、将来確認が出るようになった場合に備えて入れてある。
- 向きの決めごと：iPhone の上端を右へ振るとポインタは右へ、上へ振ると上へ動く。本体の回転（ロール）は無視する。既定の感度は 1 ラジアンあたり 1500 カウント（1 度あたり約 26）で、0.25〜4 倍に調整できる。推測値なので、利用者と調整する。
- **既存の動きを1点変えた。** 接続先を切り替えるとき、送信待ちのレポートを最大 24 件まで元の接続先へ送ってから切り替える。何かが押されたままなら「何も押していない」を送る。以前は捨てていたが、それでは離す側のキーが届かず、Ctrl などが押されたままになるおそれがあった。副作用として、文字列を送っている最中に切り替えると、元の接続先に最大 12 文字ほど余分に入る。
- 利用者が Mac で動作を確認した（2026-11-18、`App/build/run.log` 03:17〜）：スライド送り（次・前とも）、ポインターのボタン（押して ⌘L、離して ⌘A、計 10 回）。利用者は Mac 向けの感度を 1.0 から 1.7、さらに 2.0 に上げて使った。既定値の 1.0 は Mac には弱い。
- 未確認：Windows での動作（Ctrl+L／Ctrl+A、Ctrl＋左ボタン押しっぱなし）、PageDown／PageUp の設定。

片付け（2026-11-18、`swift test` は 277 件すべて通る）：

- ポインターの感度の既定を 2.0 倍にした（利用者が設定済みの値は変えない）。
- 入力内容のログ記録を既定でオフにし、既存の設定も一度オフに戻した。オフの間、打った文字・変換中の文字列・確定した文字列・読みは、文字数や種類だけを記録する。見直しで、引用符を含む文字列の一部が伏せ字から漏れる不具合などを直した（`LogRedaction`、`HIDCore`）。
- 画面の文字を減らした。メイン画面の丸いボタンの見出しと、クリッカー画面の補足表示を外し、設定の説明文を誤操作の防止に要るものだけに絞った。外した見出しは読み上げ用の情報として残してある。
- トラックパッドの面に、薄い格子と交点のドットを入れた（間隔 36 ポイント、スクロール帯には重ねない）。
- 使い方と入れ方は `README.md` に書いた。

## 9. 制約

- 前面で動かすことを前提にする。ロック中やバックグラウンドでは操作できない。
- 接続間隔は接続先（セントラル）が決める。この Mac では30ミリ秒で、レポートは30ミリ秒ごとに数件まとめて届く。ポインタの動きは毎秒33回程度の刻みになる。
- 接続間隔について、Mac のログ（`spike/fps-notes/bt-3h.log`）で分かったこと：
  - macOS は、HID サービスを見つけた直後（21:26:23）と AirPods が切れた直後（21:30:17）の2回、間隔を15ミリ秒に縮めようとした。2回とも「接続パラメータを受け入れられない」という誤り（STATUS 759）で失敗し、30ミリ秒のままになった。iPhone 側が断った可能性が高い（推定）。
  - その2回の時点で iPhone で動いていたのは最初の測定アプリで、`setDesiredConnectionLatency(.low)` を呼んでいなかった。`.low` を呼ぶアプリが動いている状態で macOS が15ミリ秒を求めたことは、まだ一度もない。「`.low` を呼んでも短くならなかった」という以前の記述は、この組み合わせを試していなかったので取り消す。
  - macOS が縮めようとするきっかけは、新しい接続で HID の初期化が済んだときと、接続中のオーディオ機器が増減したときである。アプリの起動し直しでは起きなかった。
  - **3回目（23:02:56）：`.low` を呼んでいる `HIDPad` が動いている状態で、AirPods をつなぎ直して macOS に15ミリ秒を求めさせた。結果は同じ STATUS 759 で、30ミリ秒のままだった。** 購読時に `.low` を一度呼んでおくだけでは、iOS は15ミリ秒を受け入れない。このとき iPhone は Windows とも同時につながっていた。macOS の要求内容は、最小・最大とも15ミリ秒、周辺機器側の待ち 22、監視タイムアウト 2 秒だった。
  - まだ試していない条件：Windows を切った状態での要求、`.low` を要求の直前に呼び直した状態での要求。
  - この Mac での上限は15ミリ秒（毎秒66回程度）の見込み。7.5ミリ秒は、iOS が握っている機器種別（Appearance）が条件になっていて届かないとみられる（推定）。
  - Windows は、読み取り要求の到着間隔から、15ミリ秒（または7.5ミリ秒）で動いているとみられる（推定。直接の計測ではない）。
- Apple の資料は、`.low` が具体的にどの間隔を求めるかを示していない。変更は保証されない、とだけ書いている。
- 送信が詰まると `updateValue` が `false` を返す。合算と再開は実測で正しく動き、送った合計と Mac が受け取った合計は一致した。
- 短時間に大量のレポートがまとまって届くと、macOS 側の加速度のかかり方が変わり、行って戻る動きでもカーソルが元の位置からずれることがある（合計がゼロでも約24ポイントずれた例がある）。
- iOS か接続先の片方だけがペアリング情報を失うと、つながらなくなる。直すには両側での削除とペアリングのやり直しが要る（Mac については §7.1 の注意に従う）。
- 128ビット形での登録は、公開された仕様ではなく実測に基づく挙動である。iOS の更新で変わる可能性がある。
- 既存のオープンソース実装 `darwin-bt-remote` は AGPL-3.0 である。コードは写さない。HID over GATT の仕様から自前で実装する。

## 10. ビルド・署名・配備

- プロジェクトは xcodegen（`project.yml`）で生成する。`.xcodeproj` は手で書かない。
- 署名は自動署名。チーム ID は証明書の OU から読む。
- プロファイルの期限は実測で1年だった。7日ごとの再署名の仕組みは作らない。期限切れのときは同じ手順でビルドし直す。
- 手順（`spike/hid-probe` で通ったもの）：

```
xcodegen generate
xcodebuild -project <名前>.xcodeproj -scheme <名前> -configuration Debug \
  -destination 'id=<UDID>' -derivedDataPath build \
  -allowProvisioningUpdates -allowProvisioningDeviceRegistration build
xcrun devicectl device install app --device <UDID> build/Build/Products/Debug-iphoneos/<名前>.app
xcrun devicectl device process launch --console --terminate-existing --device <UDID> <バンドルID> [-- 引数...]
```

- `--console` を付けると、アプリの標準出力が端末に返る。アプリは終了しないので、バックグラウンドで実行してログをファイルに取る。
- zsh では `log` が組み込みコマンドなので、macOS のログは `/usr/bin/log` で読む。
- iPhone 側の前提：デベロッパモードがオン、ロック解除、USB 接続。

## 11. テスト

### 11.1 単体テスト（実機不要）

`Packages/HIDCore` で `swift test`。対象は次のとおり。

- Report Map のバイト列（仕様どおりの固定値と比較）
- 各レポートのバイト列への変換、値の範囲の切り詰め
- `PointerEngine`：タッチの列を与えて、出てくるレポートの列を比較
- `KeyMap`：US と JIS の両方で、ASCII の全文字が期待どおりのキー操作になること
- `ReportQueue`：送信待ちの間の移動量の合算、キー操作の順序の保持

### 11.2 実機テスト

CoreBluetooth の周辺機器の役割はシミュレータでは動かない。通信を通すテストはすべて実機で行う。

- Mac 側の観測は `Tools/mac-connect` の監視モードで行う。IOHIDManager で、転送方式が Bluetooth Low Energy のデバイスだけを開き、届いた入力値を記録する。カーソル座標の観測より確実で、利用者自身のトラックパッド操作と区別できる。
- iPhone 側は、起動引数で決まった入力列を自動送出するテストモードを持つ。
- キーボードの監視には、Mac の「入力監視」の許可が要る。この Mac の端末アプリには付与済みである。
- 文字入力の自動テストは、`mac-connect monitor --seize` で BLE の HID デバイスを占有してから行う。占有中は、iPhone からのキー入力が監視ツールにだけ届き、前面のアプリには届かない。占有できたことを F13 で確かめてからでなければ、文字キーを送ってはならない（§11.3）。

### 11.3 テストの安全規則

**自動テストで送った入力は、その時点で Mac の前面にあるアプリに届く。** 作業中の端末を壊さないよう、次の規則を守る。

- 送ってよいキー：F13〜F20、修飾キー単体、Caps Lock（偶数回押して元に戻す）
- 送ってはならないもの：文字キー、Return、Tab、Esc、矢印、削除、修飾キーとの組み合わせ、マウスのボタン
- 例外：`mac-connect monitor --seize` でデバイスを占有し、F13 がシステムに届かないことを確かめた場合に限り、印字可能な ASCII 文字と Shift・Option との組み合わせを送ってよい。その場合も Return、Tab、Esc、矢印、削除、Command・Control との組み合わせ、マウスのボタン、メディアキーは送らない
- 自動テストでは、送り先を必ずこの Mac に固定する（`--active-central`）。ほかの接続先には送らない
- ポインタ移動は小さく（合計で数百ピクセル以内）、スクロールは上下1目盛りずつで元に戻す
- Mac の Bluetooth を切る・Mac をスリープさせる操作は、利用者の了承なしに行わない（接続中のイヤホンが切れ、作業中のセッションも止まる）

### 11.4 手動テスト

Windows でのペアリングと操作感、Mac での実際の操作感（加速度、スクロール、ドラッグ）は、利用者が手で確かめる。確認項目は各マイルストーンの完了時に示す。
